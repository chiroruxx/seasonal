# PR の作成・更新

`AGENTS.md` とメインからの依頼を確認する。実装担当とは別の作業エージェントが、独立レビューと `pre-pr-check` の成功確認後の PR 作成・更新を担当する。本文のパスはプロジェクトルート基準。

## 入力と対象の確認

- 対象ストーリー・計画のステップ、対象リポジトリ、ブランチとコミット、独立レビュー結果、`pre-pr-check` の成功結果と対象コミット、検証証跡、先行する PR・スタック、作成または更新する範囲をメインから受け取る。
- 全ステップの実装・独立レビューと `pre-pr-check` が完了した後に、ステップごとの PR をまとめて作成する。途中のステップだけを先に公開しない。
- 公開する差分とコミットがレビュー対象と一致し、必要な指摘対応・再レビュー・検証が完了しているかを確認する。未レビューの変更や対象の版に対応しない証跡があればメインへ返し、公開を進めない。対象コミットや差分が変わった場合は、メインへ返して必要な再検証・再レビューと `pre-pr-check` の再確認を受ける。確認済みのチェックを重複実行しない。
- 機能やテストを修正しない。実装修正が必要なら coder へ戻し、再検証・独立レビュー後の依頼を待つ。受け入れテスト作成工程では PR を作成しない。

## 作成と更新

- PR の作成・更新・確認には GitHub CLI の `gh` を使う。`gh pr create`、`gh pr edit`、`gh pr view` を使い、必要な API 操作は `gh api` で行う。利用環境の `gh` や API で必要な操作を行えない場合は、未完了の操作をメインへ報告する。
- 本文は [.github/pull_request_template.md](../../../.github/pull_request_template.md) に沿って作成する。各項目を実際の変更と証跡で埋め、対象外は理由を記載し、記入案内のコメントは除く。更新時は既存の本文を読み、人間が追記した情報を保持する。
- 完成した本文を実際の改行を持つ一時ファイルに書き、`gh pr create` または `gh pr edit` の `--body-file` で渡す。タイトルは解決する問題や実現する振る舞いを簡潔に表し、本文とは別に指定する。

- レビュー済みのコミット構成を保ち、ステップ単位で PR を作成する。既存 PR があれば対象を確認して更新し、同じステップの PR を重複作成しない。
- 最初の PR は `master`、以降は前のステップのブランチを対象とし、GitHub の正式な Stacked Pull Requests として登録する。
- base ブランチの依存関係を作るだけで完了とせず、GitHub のスタック表示または API で所属と順序を確認する。
- 本文はスタック全体と当該 PR の差分を混同せず、そのステップの内容を記載する。
- PR 作成後の修正は coder が行い、独立レビュー後のコミットを受け取って更新する。先行ステップの修正があれば後続の差分・依存順序への影響を確認する。後続コミットの書き換えなどでレビュー対象が変わる場合は、メインへ戻して再検証・再レビューの範囲を確認する。
- 利用環境が未対応、またはスタックへの登録を確認できない場合は、その状態をメインへ報告する。通常の依存 PR を正式なスタックとして報告しない。
- 最後にスタック全体を提示し、別の総括 PR は追加しない。PR のマージは人間が行う。

## 報告

PR の URL、対象ステップ、head・base と対象コミット、確認したレビュー・検証証跡、スタックの所属と順序、未完了・未確認事項をメインへ返す。
