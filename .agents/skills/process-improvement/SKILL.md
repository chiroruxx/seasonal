# ストーリー完了後の改善

人間によるストーリー受け入れ後、次のストーリー着手前にメインが改善工程を担当する。判断・更新の権限はメインにあり、各工程をサブエージェントへ割り当てる通常原則の明示的例外とする。

## 判断

- 対象ストーリーの `docs/stories/<id>/work-log.md` を参照し、既存の進捗記録があれば必要事実を統合する。どちらもない場合、本工程の判断と結果を残すため work-log.md を新設する。
- 記録された失敗・手戻り、人間レビューを含む確認済み事実と根拠を確認する。原因が仮説なら仮説として扱う。
- 改善候補がある場合も、プロジェクト全体またはレイヤー全体に適用でき、根拠がある再発防止策に限る。特定ファイルや特定処理だけの規則を追加しない。
- 既存ルールとの重複、過剰な拘束、ルール追加の維持負担を確認する。既存ルールの整理・明確化で足りる場合は新しいルールを増やさない。
- 個別の不具合修正と一般的なガードレールを区別する。改善候補がなければ無理に提案・変更を作らず、変更なしで完了する。
- 判断の採否が既存の明示的な決定・確定仕様に抵触する場合は、独断で変更せず人間へ戻す。

## 変更と確認

改善を採用する場合、根拠に沿って共通文書、スキル、エージェント定義、hooks、静的解析や共通テスト基盤など必要な範囲を更新する。特定の不具合修正をこの工程へ広げない。作業記録には必要事実のみを統合して保存し、会話全文、重複、秘密情報を含めない。記録の同時編集を避け、引き継ぎには短い要約と保存先を記す。

変更は作業したメインとは別のレビュー担当が独立レビューする。変更対象に応じて `document-review`、`code-review` などを使い、適用形式・用語・リンク、formatter・linter・必要なテストの結果を確認する。有効な hooks 証跡を使い、同じチェックを重複実行しない。失敗通知には対応し、未発火・未接続は成功扱いにしない。

## PR と記録

作業記録は事象・日付、根拠、確認済み原因または仮説、試行と結果、人間レビューの要点を必要に応じて記す。既存の進捗記録へ統合し、記録先がなければ判断に必要な記録を新設する。改善工程の記録は採否理由、変更、検証、PRまたは変更なしを記す。候補なしの場合は短い変更なし記録でよい。

レビュー済み変更がある場合、メインは別のレビュー担当による独立レビュー後、別のPR作成担当へ [pull-request スキル](../pull-request/SKILL.md)の改善PRモードを依頼する。PRは通常の `main` 向けとし、受け入れ済みコミット・機能スタックと別にする。マージは人間が行う。PR作成後、採否理由、変更、検証、PRを作業記録へ追記して工程を完了する。
