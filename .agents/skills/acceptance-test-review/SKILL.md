# 受け入れテストのレビュー

`AGENTS.md`、対象ストーリーと受け入れ条件、対象テストと条件との対応、比較範囲、検証結果を確認する。作業担当とは別のエージェントとして、成果物を編集せずレビューする。本文のパスはプロジェクトルート基準。

本番の実装コードは参照しない。仕様、公開された操作・表示の契約、既存の受け入れテスト、テスト基盤は参照してよい。必要な契約や仕様が足りない場合は、実装から補わずメインへ返す。実装と単体テストのレビューには `code-review` を使い、受け入れテストだけのレビューに併用を必須としない。両方を変更した場合はスキルを併用し、本番実装の確認は `code-review` の範囲で行う。

## 確認すること

- すべての受け入れ条件から対応するテストを追い、検証漏れがないかを見る。条件名との対応だけでなく、実際の操作とアサーションが条件を検証するかを確認する。仕様が曖昧な箇所をテスト側で新しい仕様として決めていないかを見る。
- 利用者から観測できる表示・操作・結果を検証しているかを確認する。内部メソッドの呼び出しや特定の実装構造だけを期待値にしていないかを見る。
- 前提、入力データ、操作、期待値が受け入れ条件と公開契約に合っているかを確認する。条件に関係する月・年の境界や状態の違いを検証できるデータか、意図せず別の振る舞いを成功と判断する期待値になっていないかを見る。
- 対象の振る舞いが欠けている場合に失敗するテストかを確認する。アサーションの欠落、期待する結果そのものの固定・モック化、例外の握りつぶし、対象に届かない操作による偽陽性を指摘する。
- テスト間の実行順序や残存状態、端末の現在日時、外部通信など、条件に不要な不安定さへ依存していないかを見る。必要な状態を制御しつつ、検証対象の振る舞いを置き換えていないかを確認する。
- hooks の証跡が対象の版・テスト・実行範囲に対応しているかを確認する。`@PendingAcceptance` などで除外された通常チェックの成功を、対象テストの実行証拠としない。確認済みのチェックを重複実行せず、明示実行が必要ならメインへ返す。
- 未実装による想定した失敗は、条件が要求する振る舞いの不足で失敗しているかを見る。コンパイル・起動・環境エラーやテスト自体の不備を想定した失敗とせず、formatter・linter の失敗、hooks の未発火・未接続、未実行と区別する。未実装なのに成功した場合も、既存の公開された振る舞いで満たされる条件なのか、テストが機能を検証していないのかを確認する。

## 報告

指摘は対象の受け入れ条件、テストのファイル・行、根拠と影響、重要度を結び付けて示す。指摘がなくても、条件の網羅、確認範囲、テスト実行と品質チェックの証跡、想定した失敗とそれ以外の失敗、未確認事項を報告する。人間の受け入れテスト確認や、実装後の受け入れ判断を代行しない。
