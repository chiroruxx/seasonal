# テスト方針

## 機能の受け入れテスト

Compose UI Test を使い、利用者の操作に沿って自動検証する。Android 16（API 36）のエミュレーターを Gradle 管理の端末として定義し、ローカルと CI で同じ条件で実行する。

テストの日付と食材データは固定し、実行した日の月や同梱コンテンツの変更に結果が左右されないようにする。現在日時は差し替え可能な窓口を通して取得する。

| シナリオ                   | 確認内容                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| 今が旬の食材を見る         | 11月に固定すると、11月が旬の食材が「いまが 旬」に表示される                              |
| これから旬になる食材を見る | 今月は旬ではなく来月から旬になる食材が「そろそろ 旬」に表示される                        |
| 食材の選び方を見る         | カードをタップすると、対応する食材名・選び方の説明と画像を含むモーダルボトムシートが開く |
| シートを閉じる             | 閉じるボタン・背景タップ・下スワイプで閉じられる                                         |
| 一覧で買い物を続ける       | シートを閉じた後も一覧のスクロール位置を保つ                                             |

## 実装前に作成する受け入れテスト

受け入れテストは機能の実装前に作成する。未実装のシナリオは `@PendingAcceptance` で明示し、対応するストーリーの ID を記録する。

作成時には PR を作成せず、人間のレビューを待つ。確認後に開発プランを作成し、その時点から受け入れテストの内容を固定する。変更が必要なら事前に人間の承認を得る。工程の詳細は[AI 開発フロー](../development/ai-development.md)に従う。

| 実行用途                      | 対象                             | 失敗の扱い                                         |
| ----------------------------- | -------------------------------- | -------------------------------------------------- |
| 通常のチェック・PR の回帰検証 | PendingAcceptance を除くテスト   | 失敗でチェックを落とす                             |
| 開発中の対象シナリオの確認    | 対象の未実装テストを明示的に選択 | 実装前は失敗を確認し、実装後は成功を確認する       |
| ストーリー完了の確認          | 対象ストーリーの全受け入れテスト | 未実装扱いのまま完了にしない。全件成功を必須とする |

AndroidJUnitRunner の `annotation` / `notAnnotation` フィルターを使い、通常実行では未実装テストを除外し、明示実行では除外を解除できる構成にする。Gradle 管理端末の実行にも同じ区分を適用する。実行コマンドは基盤実装で用意する。

- 未実装テストもコンパイルできる形で作成する。存在しない本番 API の参照によるコンパイルエラーは、実行フィルターでは回避できない。
- `@Ignore` や失敗の握りつぶしではなく、実行対象の選択で通常チェックから分ける。
- 未実装として除外した件数とストーリーを確認できるようにし、通常チェックの成功を全機能の受け入れ完了と混同しない。
- 実装後、対象テストの成功を確認して `@PendingAcceptance` を外す。この解除だけはテスト内容の変更制限の例外とし、人間の承認なしで行える。以後は通常チェックと CI の回帰検証に必ず含める。
- 開発プラン作成後の `@PendingAcceptance` の追加・再付与や、テスト本文・期待値・操作・データなどの変更には、事前に人間の承認を得る。
- 既に受け入れ済みのテストが失敗した場合、チェックを通す目的で未実装扱いに戻さない。

## ロジックの単体テスト

JUnit で、画面から独立した旬の判定を確認する。

- 現在月の食材の抽出。
- 来月から旬になる食材の抽出。
- 今月も来月も旬の食材を「そろそろ旬」に重複させないこと。
- 12月から翌年1月への切り替わり。

## 同梱データのテスト

固定データによる UI テストとは別に、アプリの実際の同梱 JSON を読み込むテストを用意する。

- kotlinx.serialization でデータモデルに変換できること。
- 食材 ID が重複しないこと。
- 元データを確認して定める旬のデータ構造に対して、値が妥当であること。月配列を使う場合は、月が1〜12であること。
- 食材から参照する一覧画像・説明画像が存在すること。

## 人による確認

機能テストの合格だけで、次の項目を満たしたとは判断しない。

- 色鉛筆の絵が親しみやすく、食材を見分けられること。
- 画面の配色や文字が見やすいこと。
- 小学生にも説明が伝わり、迷わず操作できること。
- 旬・選び方の内容が出典に照らして正しいこと。

実機・エミュレーターでの確認と、必要に応じた利用者による確認を組み合わせる。
