# エージェントとスキルの構成

## 定義の分担

- `AGENTS.md`：変更制限、開発フロー、設計文書への参照など、全エージェントに共通するルール。
- エージェント定義：担当範囲、入力、成果物、完了条件、報告形式。
- スキル：特定の作業に必要な手順と確認観点。
- 個別の依頼：対象ストーリー・ステップ、変更可能な範囲。

共通ルールを役割ごとに複製せず、共通の定義と文書を参照する。共通ルール、6種類のエージェント定義、11種類のスキルをリポジトリ内に配置している。

役割・スキルの実行時定義から、iteration0 内の検討文書は参照しない。この整理のために検討文書を別の場所へ移設しない。必要な作業手順はスキルに置く。

定義の自動検出と、役割名・スキル名による実動作は別途確認する。hooks は `PostToolUse` と `Stop` に接続し、[checks.json](../../../../.codex/hooks/checks.json) で対象とコマンドを管理する。`connected` はコマンドの接続状態であり、ホストでの信頼・自動発火や、実行成功を保証しない。状態が `pending` のコマンドは未接続として扱う。実装・文書作成担当に同じチェックの手動実行を重複させず、未接続・未発火はメインへ報告する。実行入口・有効化・証跡の確認は[品質チェックと hooks](../../../development/quality-checks.md)に従う。

## エージェント

| 役割               | 入力                                                             | 担当・成果物                                                           | 完了時の報告                                 |
| ------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------- |
| メイン             | 人間の依頼、各工程の成果物・レビュー結果                         | 進行管理、担当割り当て、引き継ぎ、人間への確認                         | 現在の工程、確認結果、人間の判断が必要な事項 |
| 受け入れテスト作成 | ストーリー、受け入れ条件、テスト方針                             | 受け入れ条件から観測できる振る舞いのテスト。機能実装は参照・変更しない | テストの差分、条件との対応、基盤の不足       |
| 設計・計画         | 確認済みの受け入れテスト、ストーリー、設計文書                   | 詳細設計と、価値単位の小さな実装ステップ                               | 分割内容、依存関係、検証方法                 |
| コーディング       | レビュー済みの計画、担当ステップ、変更可能な範囲                 | 本番コード・必要な単体テストの実装、hooks の指摘への対応               | 変更内容、hooks の失敗や未発火、未確認事項   |
| ドキュメント作成   | ユーザーの依頼・明示的な決定、指定資料、対象文書、変更可能な範囲 | 文書の作成・更新、用語やリンクの整合                                   | 更新内容、整合性の確認結果                   |
| レビュー           | 対象成果物、仕様・設計、検証結果                                 | 対象に応じたスキルによる独立レビュー、hooks の検証証跡の確認           | 指摘、根拠、検証結果の妥当性、未確認事項     |
| 調査               | 調査目的、対象範囲、必要な情報                                   | 情報収集、比較、根拠付きの調査報告                                     | 出典、確認できた事実、不一致、不足、提案     |

改善工程を除き、AI のみで作業する各工程は作業サブエージェントが担当し、作業担当とは別のエージェントがレビューする。メインエージェントが工程間の整合性と人間の確認待ちを管理する。受け入れ後の改善判断・更新はメインが担当し、別のレビュー担当が確認する。工程の完了条件は[AI 開発フロー](ai-development.md)に従う。

## 作成用スキル

コーディング担当は `coding`、文書作成担当は `document-writing` を使う。全ステップの実装と独立レビュー完了後、reviewer が `pre-pr-check` で最終確認する。メインが成功を確認した後、実装担当とは別の作業エージェントへ `pull-request` スキルで機能PRの作成・更新を依頼する。受け入れ後の改善PRではメインが判断・更新し、独立レビュー後に別のPR作成担当へ依頼する。PR 作成専用のエージェント定義は追加しない。エージェント定義は担当範囲を、スキルは具体的な手順と完了条件を持つ。

機能PR作成担当はレビュー済みコミットと検証証跡を確認し、正式な Stacked pull requests の登録・説明・順序を管理する。改善PRは通常の `master` 向けPRとし、機能スタックに含めない。機能PR作成後の実装修正は coder が担当し、再レビューと `pre-pr-check` の再確認後に PR 作成担当が更新する。

文書の形式は、対象ディレクトリからリポジトリルートまでの祖先にある `FORMAT.md` を確認し、対象に近い具体的な指定を優先する。形式がない場合は依頼と同種の既存文書に沿い、依頼なく形式ファイルを新設しない。詳細は文書作成スキルに置く。

## レビュースキル

レビューエージェントの定義は1種類とし、対象に応じてスキルを使い分ける。受け入れテストには `acceptance-test-review`、実装と単体テストには `code-review` を使う。全ステップ完了後の PR 作成前には `pre-pr-check` を使う。開発プランには `planning-review` と `document-review` を併用する。コードと文書の両方を変更した場合は、両方のスキルを使う。同じ定義を使っても、作業担当と同じエージェントに自己レビューさせない。

| スキル                 | 主な確認観点                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| 受け入れテストレビュー | 受け入れ条件の網羅、操作・期待値・データ、観測可能な振る舞い、実装からの独立性、実行証跡 |
| コードレビュー         | 受け入れ条件、不具合、責務分離、単体テストの妥当性、formatter・linter の結果             |
| PR 作成前の最終確認    | 全チェックの成功、受け入れテストの除外・未実装なし、レビュー・検証・公開対象の一致       |
| 計画レビュー           | 受け入れ条件の網羅と検証方法、価値単位の分割、ステップの大きさ、実現可能性、依存関係     |
| 文書レビュー           | 内容の正確さ、文書間の整合性、決定事項と提案の区別、形式への準拠、読みやすさ、リンク     |
| 旬データレビュー       | 原データとの対応、出典、粒度、構造と値の整合性、加工内容                                 |

レビューの進め方と報告形式はエージェント定義に、対象別の確認手順はスキルに置く。レビュー担当は対象コミットと変更範囲に対応する hooks の実行記録を確認し、formatter・linter・必要なテストの結果を判断する。対応する証跡があれば同じチェックを再実行しない。

## 調査と旬データのスキル

調査エージェントは汎用の役割とし、旬データの調査・取得には専用スキルを使う。

### 旬データ調査・取得スキル

出典の探索、データ取得、旬の定義・粒度・地域差の確認、アプリ向けの整理を行う。

- 出典・取得日・利用条件を記録する。
- 原データと、アプリ向けに加工したデータを分けて保存する。
- 地域・産地・品種・旬の期間など、元データの区別を勝手に落とさない。
- 出典間の食い違いや不足を推測で埋めず、報告する。
- データ構造の提案と、内容の採用判断を分ける。
- 詳細なデータ構造は、元データの意味と粒度を確認して提案する。[食材データの管理](../technology/food-data.md)に従う。

大量データを扱えるよう、原データと加工データを分け、出典情報と各レコードの対応を残す。成果物の形式は [旬データ調査・取得スキルの出力形式](../../../../.agents/skills/data-research/references/output-format.md)で定める。加工レコードは JSONL とし、元データの期間や地域などを保持する。アプリに同梱する JSON のスキーマとは分ける。

調査結果のデータセットは、別のレビューエージェントが `data-review` で確認する。報告書の文章は `document-review` で確認し、生データの検証と文書の検証を分ける。両方を変更した場合は両方のスキルを使う。
