# 開発フローと CI

## CI

GitHub Actions を使用する。

PR では以下を検査する。

- Spotless、Android Lint、markdownlint-cli2、Prettier。
- 単体テストと同梱データの検証。
- Debug APK のビルド。
- Gradle 管理の Android 16 エミュレーターによる受け入れ済みシナリオの回帰検証。

実装前に作成する未実装シナリオは、通常のチェックから明示的に分ける。開発中の実行方法と受け入れ済みへの移行は[テスト方針](../technology/testing.md)に従う。

## ストーリーの進め方

1. 人間と AI が協力して、ユーザーストーリーと受け入れ条件を定義する。自動テストと人による UI・UX の確認観点を整理する。
2. AI が受け入れテストを作成し、PR を作成せずに人間の確認を待つ。この段階では機能を実装しない。未実装シナリオの扱いはテスト方針に従う。
3. 確認後、AI が詳細設計と開発プランを作成する。作業はレイヤーではなく価値のある小さなステップに分ける。
4. AI が各ステップを実装し、対象テストと通常チェックを実行して、ステップごとの PR を依存順に積み重ねる。具体的な手順は [AI 開発フロー](ai-development.md)で定める。

1つのユーザーストーリーが複数の PR に分かれることを前提とする。成果物の UI・UX はユーザーストーリー単位で人間が確認する。

最初はユーザーストーリーを直列に進める。進行中のストーリーを人間が受け入れてから次のストーリーに着手する。ストーリー内で複数の PR に分けることは許容する。

## 統合・受け入れ・配布の整理案

| 単位                 | 確認すること                                                                 |
| -------------------- | ---------------------------------------------------------------------------- |
| PR の統合            | CI とコードレビューを通し、master にマージする                               |
| ストーリーの受け入れ | 関連 PR がそろった版で、全受け入れテストの成功と人による UI・UX の確認を行う |
| 端末への配布         | 配布する版を固定し、起動・主要操作を確認して自分の端末にインストールする     |

関連 PR・確認対象コミット・確認用 APK・確認手順・確認結果は、ストーリーの README.md とは別の記録にまとめる。修正が必要なら追加 PR で対応し、新しい版で再確認する。確認用 APK を用意する方法は[配布フロー](release.md)で整理する。

受け入れテスト作成時からユーザーストーリーの README.md を、開発プラン作成時から受け入れテストの内容を変更しない。変更が必要な場合は、変更前に人間へ確認し、承認を得る。

対象テストの成功確認後の `@PendingAcceptance` 解除だけは例外とし、承認なしで行える。詳細は[テスト方針](../technology/testing.md)に従う。

AI が担当する各工程は作業用サブエージェントが行い、別のエージェントが独立レビューを行う。メインエージェントは工程・引き継ぎ・人間の確認待ちを統括する。

実行用の Gradle 設定と GitHub Actions ワークフローは、基盤実装で追加する。

## 依存関係の更新

Renovate を使用して依存関係の更新 PR を作成する。

- Gradle のライブラリとプラグインは `gradle/libs.versions.toml` でバージョンを管理する。
- Gradle Wrapper も更新対象にする。
- Markdown 用の開発ツールは `package.json` とロックファイルでバージョンを固定し、両方を更新する。
- 更新 PR では通常の CI を実行する。
- 自動マージはせず、変更内容と CI の結果を確認して取り込む。画面に影響する更新は見た目も確認する。
- 破壊的変更と、AGP・Kotlin・Compose などの互換性を確認する。

Renovate の設定ファイルと GitHub 側の接続は、基盤実装で用意する。
