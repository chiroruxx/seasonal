# 配布フロー

## 配布先

最初は自分の Android 端末のみとする。

## APK と署名

- 最初は Debug APK を使い、成果物の確認と自分の端末への配布を兼ねる。
- 同じ署名鍵を継続して使う。CI の実行ごとに新しい鍵を生成しない。
- 署名鍵は Git に含めず、GitHub Actions では Secrets から復元して使う。
- 同じアプリを上書き更新するため、applicationId と署名鍵を維持し、配布ごとに versionCode を増やす。

## APK の保存と識別

- GitHub Actions の成果物として確認用 APK を保存する。
- ファイル名や実行結果から、対象ストーリーとコミットを特定できるようにする。
- 人が受け入れた APK を配布対象とし、受け入れたコミットにタグを付ける。
- 配布した APK と確認対象コミットの対応を記録する。

## ストーリーの進行と配布

最初はストーリーを直列に進め、受け入れ後に次のストーリーへ着手する。1ストーリーに必要な変更は、複数の PR に分けて統合できる。

配布対象は、ストーリーの受け入れが完了したコミットとする。次のストーリーの実装が始まっていても、その途中の変更を含むコミットを配布対象にしない。

## 手順案

1. ストーリーに必要な PR を統合する。
2. 確認対象コミットの自動チェックと、対象ストーリーの全受け入れテストを実行する。
3. 同じコミットから Debug APK を作成し、関連 PR・確認手順とともに提示する。
4. 人が実機またはエミュレーターでストーリー単位の UI・UX を確認する。
5. 配布対象のストーリーが受け入れ済みであることを確認し、配布するコミットをタグで固定する。
6. 配布対象の版で回帰テストと起動・主要操作を確認し、受け入れた APK を自分の端末への配布版とする。確認にエミュレーターを使った場合は、実機にもインストールして確認する。

確認したコミットと APK の対応を記録する。確認後に修正した場合は、新しい版を確認する。

確認用 APK の作成・保存は GitHub Actions で自動化する。具体的な設定と署名鍵の登録は基盤実装で用意する。
