# AI を使った開発フロー

ストーリーと受け入れ条件は人間と AI が協力して定義する。最初はストーリーを直列に進め、現在のストーリーを人間が受け入れてから次へ着手する。

## 役割分担

各役割の入出力と、レビュー・旬データ調査のスキル構成は[エージェントとスキルの構成](agents-and-skills.md)を参照。

| 担当                 | 役割                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 人間                 | ストーリーと受け入れ条件の定義、受け入れテストのレビュー、仕様変更の判断、成果物の UI・UX 確認、マージを行う                |
| メインエージェント   | 全体の進行、サブエージェントへの引き継ぎ、レビュー結果の確認、人間への報告と確認待ちを管理する                              |
| 作業サブエージェント | 各工程の成果物を作成し、hooks の指摘へ対応する。未接続・未発火をメインへ報告する                                            |
| レビューエージェント | 作業を担当したエージェントとは別の立場で、各工程の成果物と、対象コミット・変更範囲に対応する hooks の検証証跡をレビューする |

AI のみで作業する各工程はサブエージェントに担当させる。各工程では、作業担当とは別のエージェントによるレビューを行い、指摘への対応も確認する。メインエージェントは工程間の整合性を確認する。

## 1. 受け入れテストを作成する

1. 対象ストーリー、受け入れ条件、関連する設計文書を確認する。
2. 作業サブエージェントが機能実装に先行して受け入れテストを作成する。この工程では機能を実装せず、PR も作成しない。
3. テストはコンパイル可能な形にし、未実装シナリオとして登録する。対象を明示する検証は hooks で実行する。作成担当は既存の受け入れテストや公開契約・テスト基盤を参照できるが、機能実装は参照しない。
4. 別のレビューエージェントが、受け入れ条件との対応、テストの内容、hooks の実行記録からコンパイル可否と失敗の理由を確認する。
5. メインエージェントがテストの差分と検証結果を提示し、人間の確認を待つ。確認前に開発プランの作成や機能実装へ進まない。

## 2. 開発プランを作成する

人間による受け入れテストの確認後に開始する。

- 受け入れテストでは表現されない詳細を設計する。
- 作業を、利用者に価値のあるステップに分割する。例えば「野菜の表示」「果物の表示」とし、「ハンドラー」「UI」のようなレイヤー単位の分割にしない。
- 価値のある単位を保ちながら、可能な限り細かく分ける。各ステップの変更を人間が読みやすいサイズにする。
- ステップごとに、目的、変更範囲、受け入れ条件との対応、検証方法、前のステップへの依存を記載する。
- 1ステップを1コミットに限定しない。コミットは意味のある小さな単位で、なるべく細かく行う。
- 別のレビューエージェントが、設計と分割、受け入れ条件との対応を確認する。

## 3. ステップごとに実装する

1. 作業サブエージェントが、プランのステップを受け入れ条件に沿って実装する。
2. hooks が変更に対応する整形・lint・テストと、対象の受け入れテストを実行する。作業担当は hooks の指摘に対応する。
3. 別のレビューエージェントが差分と検証結果を確認する。作業担当が指摘を修正し、再レビューを完了する。
4. 各ステップ内は意味のある小さなコミットを積み重ねる。
5. レビュー完了後、前のステップを含むブランチを基に次のステップへ進む。この段階では PR を作成しない。

未実装による想定内の失敗、回帰テストの失敗、環境により実行できなかったチェックを区別して報告する。失敗を握りつぶしたり、受け入れ条件を緩めて成功扱いにしたりしない。

## 4. PR 作成前に最終確認する

全ステップの実装・独立レビュー完了後、reviewer が [pre-pr-check スキル](../../../../.agents/skills/pre-pr-check/SKILL.md)を使う。hooks の証跡から、全ステップを含む最終コミットで定義済みの全チェックが成功し、受け入れテストが除外されず実行されていることを確認する。リポジトリ全体に未実装の受け入れテストや `@PendingAcceptance` の付与が残っていてはならない。

各ステップのレビュー・必要な検証と、最終コミットの全体検証を区別し、PR の各 head・base と公開差分が確認対象に一致するか確認する。未接続・未実行・失敗を成功としない。対象コミットや差分が変わった場合は必要な再検証・再レビューを行い、最終確認をやり直す。

## 5. Stacked PR として提示する

メインが最終確認の成功を受け取り、実装担当とは別の作業エージェントへ `pull-request` スキルで全ステップの PR 作成を依頼する。

ステップごとの PR を GitHub の Stacked pull requests として登録し、スタック表示で登録を確認する。単に PR の base を前のブランチへ向けるだけでは完了としない。PR 作成担当はレビュー済みの対象コミットと検証証跡を確認する。作成・更新・確認手順は [pull-request スキル](../../../../.agents/skills/pull-request/SKILL.md)に従う。

最後に、スタック全体とストーリーの受け入れ条件に対する検証結果を人間に提示する。利用環境で公式のスタック登録が使えない場合は未完了として報告し、別の総括 PR を追加することで代替しない。

各 PR は CI とコードレビューを経て依存順に統合する。ストーリー全体の受け入れテストを確認した版の APK と操作手順を提示し、人間が UI・UX を確認する。修正時は coder が対象ステップと後続への影響を確認して修正し、必要な再検証と独立レビューを受ける。`pre-pr-check` の再確認後、メインが別の PR 作成担当へスタックと説明の更新を依頼する。

## 変更を制限する成果物

- 受け入れテストの作成を開始してからは、ユーザーストーリーの `docs/stories/*/README.md` を変更しない。変更が必要なら、理由と変更内容を示して人間に確認し、了承を得てから変更する。
- 開発プランの作成を開始してからは、人間が確認した受け入れテストの内容を変更しない。変更が必要なら、理由と変更内容を示して人間に確認し、了承を得てから変更する。
- formatter による、意味を変えない機械的な整形変更は許可する。内容や意味を変える変更には、引き続き事前に人間の了承を得る。
- 対象テストの成功を確認した後の `@PendingAcceptance` の解除だけは例外とし、人間の了承なしで行える。解除後は通常の回帰検証に加える。
- 開発プラン作成後の `@PendingAcceptance` の追加・再付与や、テスト本文・期待値・操作・データなどの変更には、事前に人間の了承を得る。
- `docs/stories/*/README.md` の内容は、作成工程にかかわらず事前了承なしで変更しない。意味を変えない formatter の整形は上記の例外に含める。

## ファイル変更時の hooks

ファイルを変更したときは、hooks を通して変更対象に対応する formatter・linter・テストを実行する。

formatter・linter は変更ファイルを対象とし、テストは変更の影響範囲に応じて選択する。formatter 自身の変更で hooks が再帰実行され続けないようにする。ステップの完了時と PR の提示前には、ファイル単位のチェックだけでなく、必要な全体チェックも hooks から実行する。

| 変更対象                  | 実行するチェック                                                             |
| ------------------------- | ---------------------------------------------------------------------------- |
| Kotlin・Gradle Kotlin DSL | Spotless + ktfmt、関連するテスト。Android の変更には Android Lint も実行する |
| Markdown                  | Prettier、markdownlint-cli2、参照リンクなどドキュメントに対応する検証        |
| 食材データ・画像参照      | 関連するデータ検証テスト                                                     |

`docs/stories/*/README.md` と確認済みの受け入れテストでも、意味を変えない formatter の整形は許可する。formatter を使って内容や意味を変更しない。未実装の受け入れテストを通常チェックから分ける運用は[テスト方針](../technology/testing.md)に従う。hooks は既存のテスト失敗を無視する仕組みにしない。

現在の hooks はイベントの空定義で、チェックは未接続である。接続と実行コマンドは基盤実装で動作確認する。未接続・未発火は検証未実施としてメインへ報告し、成功や工程完了にしない。

レビューエージェントは、対象コミットと変更範囲を満たす実行記録から formatter・linter・必要なテストの結果を確認する。有効な記録があれば同じチェックを重複実行しない。環境の不備はメインへ返し、作業担当の手動実行を前提に補わない。

## 記録の置き方の案

以下は、制限対象のファイルを変更せずに作業を進めるための案とする。

- 人間が確認した受け入れテストは、PR を作成せずにコミットとして保持し、後続スタックの最下段の実装ステップに含める。
- 開発プラン、関連 PR、確認対象コミット、APK、確認手順、確認結果は、ストーリーの README.md とは別のファイルに記録する。
